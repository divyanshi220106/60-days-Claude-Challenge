# Day 27 — Prior Authorization Story Simulator

## What I Built

An interactive, single-file HTML story simulator that walks users through a patient's complete Prior Authorization (PA) journey in the US healthcare system. The app follows **Rahul**, a Rheumatoid Arthritis patient, and **Priya**, a healthcare operations specialist, across 8 story chapters — with branching choices, animated chat bubbles, and a live progress tracker.

---

## The App: Prior Authorization Story Simulator

**File:** `prior-auth-story.html`  
**Tech Stack:** HTML · Tailwind CSS CDN · Vanilla JavaScript (no frameworks)

### Core Features

- **8 Interactive Chapters** — Doctor Visit → Insurance Roadblock → What is PA? → Insurance Review → Denial → Appeal → Approval → Takeaways
- **Branching Dialogue** — 2 choices per scene that influence conversation paths and unlock different explanations
- **Append-Only Chat Feed** — built strictly with `createElement` + `appendChild` (never `innerHTML =`)
- **Animated Progress Bar** — live chapter dot tracker updates as you advance
- **Two Characters** — Rahul (patient, left bubbles) and Priya (specialist, right bubbles); narrators as centered italic text only
- **Restart Flow** — explore all alternate dialogue paths after completing the story

## Key Healthcare Concepts Learned

### What is Prior Authorization?
A formal process where an insurance company reviews whether a treatment is **medically necessary** before agreeing to pay for it. Required for expensive medications like biologics (e.g., Humira for RA, which costs ~$6,000+/month).

### PA Flow
```
Provider (Dr. Patel's Office)
        ↓
   PA Request submitted
        ↓
  Payer (StarCare Health) reviews
        ↓
  Decision → Approved / Denied
```
No pharmacy is involved in the PA submission — it goes directly from provider to payer.

### What Payers Review
| Checkpoint | Why It Matters |
|---|---|
| Eligibility | Is the patient actively covered? Is the drug on the formulary? |
| Clinical Documentation | Are the provider's notes complete and specific? |
| ICD-10 Diagnosis Match | Does the code exactly match approved indications? |
| Step Therapy History | Has the patient tried cheaper alternatives first? |

### Step Therapy
Insurance companies may require patients to try less expensive medications first, document failure, and only then approve a biologic. For aggressive diagnoses like RA, delays in step therapy can cause **irreversible joint damage**.

### Denial ≠ Permanent
- Most denials are reversible
- You have the right to **appeal** (typically 30–60 days from denial date)
- Over **40% of insurance appeals are successful** with proper documentation
- **Peer-to-peer review** (physician to physician call) is one of the most effective reversal tools
- PA denials cost physician offices **2+ staff hours** per case to resolve (MGMA data)

### Key Stats Referenced
- **AMA 2023 PA Survey:** PA causes treatment delays in the majority of cases
- **Administrative burden:** 2+ staff hours per denial resolution
- **Appeal success rate:** 40%+ with complete documentation

### System-Level Metrics Health Organizations Track
| Metric | What It Measures |
|---|---|
| Denial Rate | % of PAs denied (benchmark: <15% = low) |
| Appeal Rate | % of denials that are appealed |
| Resolution Time | Avg days from submission to final decision |
| Admin Cost per PA | Staff hours × hourly rate (~$50–$100 per PA) |

## Technical Implementation Notes

### Architecture Decisions
- **Single HTML file** — no build step, no dependencies beyond Tailwind CDN
- **Append-only DOM** — every message is `createElement`'d and `appendChild`'d to the chat feed; no clearing or `innerHTML =` on the container
- **Staggered rendering** — `setTimeout` delays between messages create natural conversation pacing (500ms per message)
- **Scene graph** — story scenes are stored as a flat JS array with `id`, `parentScene`, `isTransition`, and `nextScene` properties for branching logic
- **Progress tracking** — canonical scene numbers (1–8) drive the progress bar; branch scenes reference their parent for correct progress calculation

### Message Types Rendered
| Type | Appearance |
|---|---|
| `rahul` | Left chat bubble (white, yellow avatar) |
| `priya` | Right chat bubble (blue tint, blue avatar) |
| `narrator` | Centered italic gray text |
| `info` | Blue left-border card |
| `stat` | Yellow warning chip (centered) |
| `denial` | Red left-border card |
| `success` | Green left-border card |
| `flow` | Visual step-therapy flow diagram |
| `checklist` | Icon + label + description card |
| `takeaways` | Dual patient/system perspective cards |

## Prompting Strategy Used

The prompt was highly structured and specific:
- Defined characters, their positions (left/right), and what narrator text looks like
- Specified the exact DOM manipulation method (`createElement` + `appendChild`, never `innerHTML =`)
- Listed all 8 scenes with exact content requirements per scene
- Called out specific citations (AMA 2023), specific statistics (2+ staff hours), and specific framing ("illustrative example")
- Required two perspectives in the final takeaways (patient + system)

**Lesson:** The more you specify the *interaction model* (not just the visual design) in a prompt, the more consistent and production-ready the output.

## Key Takeaway

Building educational simulators with Claude works best when you treat the **interaction model as a first-class design concern** — not just the content. Specifying DOM patterns, character positioning rules, message type taxonomy, and story branching logic in the prompt produces code that's consistent, readable, and extensible. The PA domain also shows how understanding healthcare operations (not just clinical knowledge) can help patients advocate for themselves effectively.
