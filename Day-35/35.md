# Day 35 — Prompt Puzzle: Master AI Prompting Through Play

## 🎯 Objective
Build and play a gamified prompt-engineering trainer to practice recognizing, assembling, and cleaning high-quality AI prompts — and to internalize *why* certain prompts outperform others.

## 🛠️ What I Built
A single-file, offline HTML/CSS/JavaScript application: **🧩 Prompt Puzzle**.

- **Domain:** Software & Tech
- **Difficulty:** Intermediate
- **Scenarios:** 6 randomized, covering real engineering tasks (debugging a memory leak, writing unit tests, refactoring React, designing a rate limiter, optimizing SQL, generating API docs)
- **Challenge types:**
  1. **Build the Prompt** — drag correct components (role, task, context, constraints, format) into place while ignoring distractor blocks.
  2. **Clean the Prompt** — remove noisy/off-topic requests from a messy prompt to reveal the optimized version.
  3. **Choose the Best Prompt** — compare Weak vs. Optimized vs. Over-Engineered prompts and their outputs, and pick the one that actually gets the job done.
- **Scoring:** Accuracy, Time, Moves, Wrong Placements, Hints Used, Optimization Bonus.
- **Prompt Performance Report:** final score, rating, rank, a "Prompt DNA" radar (Clarity, Specificity, Structure, Efficiency, Iteration), personalized feedback, next milestone, and a final optimized prompt example.

## 🧠 Key Learnings

1. **Structure beats length.** Every "optimized" prompt in the puzzle followed the same shape — *Role → Task → Context → Constraints → Output format* — while every "over-engineered" prompt failed by piling on scope, superlatives, and unrelated requests instead of precision.
2. **Distractors are the real test.** The hardest part wasn't knowing the correct blocks — it was resisting blocks that *sounded* helpful (tone requests, unrelated topics, scope creep) but diluted the actual task.
3. **"Clean the Prompt" mirrors real-world prompt debugging.** Most weak prompts I write day-to-day aren't missing information — they're cluttered with tangents. Subtracting is often more valuable than adding.
4. **Over-engineering is a real failure mode, not just under-specifying.** A prompt asking for "the greatest, most exhaustive, all-encompassing" version of something usually produces bloated, unverifiable output — matching effort to actual risk/scope matters more than maximizing detail.
5. **Constraints do the heavy lifting.** In nearly every scenario, the single highest-leverage block was a constraint (e.g., "don't suggest restarting the process," "under 150 words," "no live network calls") — constraints are what make output *usable* rather than just plausible.
6. **Gamified repetition builds pattern recognition faster than reading.** Seeing the same Weak → Optimized → Over-engineered contrast across six different technical scenarios made the underlying pattern obvious in a way a single explanation wouldn't.
